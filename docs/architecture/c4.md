# C4 model

This is the standalone product view. ByteDesk Platform is one external
consumer, not a container inside Agent Delivery.

## C1 — System context

```mermaid
flowchart LR
  Author[Agent author or catalog maintainer]
  Catalog[Definition-only Agent Catalog\nGit repository]
  Delivery[ByteDesk Agent Delivery\nheadless supply-chain and delivery control plane]
  ProductRelease[Signed contract and renderer releases]
  Registry[OCI Registry]
  ProductKMS[Product/public KMS and federation]
  ContractSigstore[Contract-release Sigstore trust service]
  Consumer[Consuming Platform]
  ConsumerKMS[Per-consumer private KMS/HSM]
  Desired[(One DesiredStateStore\nper target)]
  Capability[Consumer Capability Verifier]
  Host[Target-scoped Host Reconciler]
  Harness[Agent Harness\nHermes, OpenClaw, or other]
  Operator[Consumer operator or automation]

  Author -->|reviews tenant-free Agent Spec and public skills| Catalog
  ProductRelease -->|exact schemas, allowlist, binaries, provenance| Delivery
  Delivery -->|reads exact commit| Catalog
  Delivery -->|publishes and verifies exact digests| Registry
  Delivery -->|KMS-backed product/public purpose signing| ProductKMS
  Delivery -->|contract-bundle-release-v1 keyless signing and verification| ContractSigstore
  Consumer -->|binding, approvals, signed current authority| Delivery
  Consumer -->|owns isolated private keys| ConsumerKMS
  Delivery -->|narrow private artifact sign request; never authority/approval| ConsumerKMS
  Operator -->|intent and conditional commands| Delivery
  Delivery -->|Coordinator-only CAS writes| Desired
  Host -->|reads desired; appends technical evidence| Delivery
  Host -->|pulls by digest| Registry
  Host -->|stages and switches verified content| Harness
  Capability -->|signed permitted/denied evidence| Delivery
  Capability -->|normal candidate runtime and authorization path| Harness
```

### C2 reference deployment

The concrete reference profile is defined by
[ADR-0002](adr/0002-implementation-stack-and-reference-topology.md).

```mermaid
flowchart TB
  Ingress[Ingress / API load balancer]
  API[3+ Go API replicas]
  Worker[Purpose-separated Go worker modes]
  RenderController[Connected renderer controller]
  PG[(PostgreSQL 18\nauthority + actions + outbox/inbox)]
  Stage[(Encrypted per-attempt\ninput/output volumes)]
  Sandbox[Networkless gVisor runsc\nfresh renderer sandbox]
  RegistryAdapter[OCI Registry Adapter]
  RegistryA[Active-region Harbor HA]
  RegistryB[Recovery-region Harbor HA]
  HarborMetaA[(Dedicated Harbor\nPostgreSQL + Redis A)]
  HarborMetaB[(Dedicated Harbor\nPostgreSQL + Redis B)]
  BlobA[(Region-A live S3)]
  BlobB[(Region-B live S3)]
  Archive[(Dual-region Object Lock\nevidence archive)]
  KMS[Product and per-consumer KMS\nOIDC/WIF]
  Identity[SPIFFE / SPIRE mTLS\n3 servers + dedicated RDS/KMS/PCA]
  OTel[HA OpenTelemetry gateways]

  Ingress --> API
  API --> PG
  Worker --> PG
  Worker --> RenderController
  RenderController --> Stage
  Stage --> Sandbox
  Sandbox --> Stage
  Worker --> RegistryAdapter
  RegistryAdapter --> RegistryA
  RegistryAdapter --> RegistryB
  RegistryA --> HarborMetaA
  RegistryB --> HarborMetaB
  RegistryA --> BlobA
  RegistryB --> BlobB
  Worker --> Archive
  API --> KMS
  Worker --> KMS
  API <--> Identity
  Worker <--> Identity
  API --> OTel
  Worker --> OTel
```

API and worker replicas are stateless outside PostgreSQL leases and actions.
The Promotion Coordinator has no process-leader authority: exact target CAS and
worker fencing decide the one accepted transition. Each eligible OCI graph was
pushed and digest-read through both Harbor APIs; direct writes to Harbor's S3
layout are forbidden. Registry blobs live outside application PostgreSQL while
their exact descriptors and evidence roots live inside it. Harbor metadata and
SPIRE registration stores are isolated infrastructure planes, not product or
consumer authority.

## Dynamic view — end-to-end delivery flows

```mermaid
flowchart LR
  Authoring[Author tenant-free Agent Spec and optional public skills]
  Publication[Validate, render, evaluate, sign, and publish exact public artifacts]
  Import[Import exact source and renderer identities]
  PrivateCustomization[Apply consumer-owned functional, file, and skill operations]
  Compilation[Revalidate, fully rerender, compile, and privately sign]
  Coordinator[Promotion Coordinator verifies current gates]
  DesiredState[(One target DesiredStateStore)]
  Reconciliation[Target-scoped Host Reconciler stages exact release]
  Canary[Separate host and consumer capability evidence]
  Activation[Coordinator authorizes switch and records receipt]
  EligibleHistory[Eligible historical functional content only]
  ForwardRecovery[Build a new revision with current tooling and authority]

  Authoring --> Publication
  Publication --> Import
  Import --> PrivateCustomization
  PrivateCustomization --> Compilation
  Compilation --> Coordinator
  Coordinator -->|sole logical CAS writer| DesiredState
  DesiredState --> Reconciliation
  Reconciliation --> Canary
  Canary --> Coordinator
  Coordinator --> Activation
  EligibleHistory --> ForwardRecovery
  ForwardRecovery --> Compilation
```

The recovery edge rejoins compilation before desired state. It cannot activate
historical deployment state, signatures, authority, or credentials. The
Host Reconciler and capability verifier return evidence to the Coordinator;
neither writes desired state or promotes itself.

## Relationships deliberately absent

- Catalog or binding content cannot supply schemas, trust roots, renderer code,
  renderer redirects, consumer identity, grants, or desired state.
- Public endpoints never accept consumer customizations, private skills, or
  private authority evidence.
- Agent Delivery never executes skill files or artifact hooks. A runtime may
  expose exact-digest-approved content only after activation under current
  consumer sandbox, network, identity, and call-time authorization.
- Product/public signers cannot satisfy consumer-private signing purposes; a
  provider-wide key cannot sign multiple consumers' private artifacts.
- The KMS-only product-release signer cannot sign contract bundles, and the
  keyless contract-bundle signer cannot satisfy product-release policy.
- Agent Delivery does not issue human or workload identity, grants, business
  approval, or call-time authorization.
- Host Reconcilers do not receive desired-write, human administration, or agent
  capability permissions and cannot run consumer capability probes.
- Capability verifiers and evidence cannot promote themselves.
- No target has two authoritative desired-state stores or live dual write.
- Harnesses do not pull mutable catalog content or execute revoked renderer
  tooling.
- Recovery never reactivates an old deployment, receipt, authority snapshot,
  signature, credential state, render bundle, or revoked renderer.
